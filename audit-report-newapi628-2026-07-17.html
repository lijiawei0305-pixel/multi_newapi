📋 总体评估

项目概况： newapi628 是基于 New API（Go 1.21+ / React / MySQL 8 / 单栈 Docker Compose）二次开发的多租户 API 代理分销平台，线上仅一套生产栈 newapi_test 服务三个域名。本次审计范围是 ae18086..cbdf76e——作者 WEI 于 07-15 至 07-17 推上 origin/main 的 19 个提交、111 个文件，内容横跨死码清除、并发重构、安全修复、计费/对账与部署脚本。这不是一批常规 bugfix，而是一次高密度的自审整改：作者独立挖出并修复了 5 个 Critical（提交进 git 的生产 SESSION_SECRET、mt-router 全部自研路由旁路限流、代理页脚存储型 XSS、兑换码 int64 溢出铸币、违禁词只覆盖 2/11 种请求格式），把 CLAUDE.md 的 C1–C7 硬约束从 TODO 占位填成了实条款，并纠正了 STATUS.md 里「internal/risk 是死码」的死活反转误判。

主要风险： 三类。其一是本批引入的真回归——checkTrialLimit 从「先 Get 预检不写」改成「逐维 SetNX 边查边写」后，被实名/设备维度拒绝的败者已把自己的用户键（TTL=0 永久）写死，正常用户一次共用设备即被永久锁死、且提示是「已超过限购次数」这句谎话；Redis 抖一下同样永久吃掉终身 Trial。其二是本批新代码没堵住它宣称堵住的洞——AGT slug 预检只查 tenants.slug 不查 tenant_domains.domain、且是无预留的 check-then-act，两个买家可预检同一 slug、双双被扣 ¥9990、只有一个能激活；新 AGT 对账在查单故障时把已付款订单静默标成 expired 且 Failed 为空导致告警不响。其三是新装的防护根本没通电——本批给 4 个 money 端点加的 CriticalRateLimit 全部按 c.ClientIP() 计桶，而全仓从未调用 SetTrustedProxies、gin 默认信任 0.0.0.0/0、nginx 又是追加 XFF，攻击者每请求换个头即落进全新桶；反过来因桶 key 不含路由成分，任何未认证者可把任意 IP 从整个 /api 面踢下线。此外一条历史遗留的 Critical 被本批新测盖了绿章：全仓 17 处 tx.Set("gorm:query_option", "FOR UPDATE") 是 GORM v1 写法，v2（本仓 v1.25.2）静默忽略——整个仓库没有一把生效的行锁。

亮点： 这批改动的工程质量显著高于其提交信息所暗示的水平，且多处经得起对抗性复核。死码清除是干净的：internal/relay/identity/billing 各为闭合孤岛（外部 importer 数 0，Go 语义下即零引用铁证），go vet ./... 输出与基线逐字节相同，被删的「安全守卫」从未接线过（线上鉴权一直是原生 UserAuth/AdminAuth，27 处）——那个覆盖死码的绿测试反而是有害的虚假保障。SetNX 重构的核心主张是成立的：200 轮 × 32 并发差分实测，旧码单轮可发出 3 份 Trial，新码严格 1 份，确实堵死了一个真实的跨账号并发绕过。npm overrides 迁根真的修好了东西：bun 只认 workspace 根的 overrides，11 条安全 pin 放在成员包里时根本没生效，bun.lock 实证 brace-expansion 1.1.15 → 2.1.1 等现已真正绑定。违禁词抽取没有绕过，且还堵掉了两个真实旧洞（旧码只扫最后一条 user 消息）。新增的钱相关测试是真测试：5 次变异（去掉 RowsAffected 守卫、翻转溢出判断、还原嵌套事务、放宽额度闸门、去掉 CAS 状态条件）全部被捕获。cbdf76e「修复落 main 前两处红测」是正当修复，非把测试改绿：全 diff 只动两个 _test.go，删掉的断言指向的代码路径确已随重构消失，其语义由相邻的 SetNX 错误传播测试承接。

优先修复： 按「代价/收益」排序。立刻：① 别去补 deploy.sh 那个 warn: command not found——当前「假成功部署」唯一的拦阻就是这个未定义函数的崩溃，补上 warn() 会当场把 07-16 那次「报成功却跑旧码」的事故放回来；正解是把运行中容器的版本自检从 warn 改成 die（其余零件已就位并验证正确）。② checkTrialLimit 加 6 行 acquired 回滚（Del 原语就在同一批加的，注释「KVCache 无删除原语」已过时）。③ restore.sh 在强制预备份前把恢复目标拷到临时区，否则恢复第 7 新（最旧）快照时会把它自己剪掉。本周：④ 17 处 gorm:query_option 机械换成 clause.Locking，配一个 DryRun 断言 SQL 含 FOR UPDATE 的守卫测试（毫秒级钉死整类）；⑤ 4 个 money 端点改用仓库已有的按 user_id 计桶的 userRateLimitFactory，并补 SetTrustedProxies；⑥ AGT 对账仅在 ErrOrderNotExist 这类确定性答复下才 expire，其余留在 pending 且进 Failed 以触发告警。

总评： 5.0 / B（Fair — 需要投入，但不需要推倒重来）。这批改动净值为正：它真的修好了 5 个 Critical、真的堵死了一个并发绕过、真的删干净了 1652 行伪装成正主的死码。分数被压在 B 而非 A，是因为三条并存的系统性问题——修复引入了比原 bug 更持久的新伤（Trial 永久误封无自助恢复）、修复宣称的边界与实际不符（AGT 预检、限流、注释里的「已锁定订阅」/「无删除原语」/「同基础链」多处与代码实情相反）、以及绿测试为不生效的机制背书（行锁空操作、SetNX 重构可整个还原而 CI 全绿）。值得注意的是，作者自己在 RETRO 中已识别出「清单挑选式遗漏＝漏一个即绕过」这一反复出现的模式并升级为 C2/C3/C5——而本次的 AGT 预检漏查 domain、限流漏了 trusted proxy、Trial 漏了回滚，正是同一个模式的第四、五、六次复发。建议把该模式本身固化为 C8（当前仍空着），并在合入前补上跨账号并发测试与 AGT 对账测试这两处 High 缺口。合入建议：Request changes——本批不含「必须阻断」的新 Critical（唯一 Critical 为历史遗留），但 10 条 High 中有 3 条会直接吃掉真实用户的钱或权益，应在部署前先修 ①②③。
