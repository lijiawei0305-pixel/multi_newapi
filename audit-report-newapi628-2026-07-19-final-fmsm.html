R01. 已修复：原生订阅订单已固化不可变结账/权益快照，并按已验证支付事实完成

Resolved Confidence: High
📁 Category: Data Integrity / Payment 📌 Status: Remediated · Code-level verified ⚠ Historical severity: High 📍 Affected area: model/subscription*.go；controller/subscription_payment_*.go；controller/topup_*.go；router/api-router.go
Problem（历史）：下单时的套餐权益曾不是订单的不可变事实，回调完成时会读取可能已被管理员修改后的当前套餐；模型完成接口也缺少统一的网关金额、币种、产品与模式事实。
Evidence： model/subscription.go:108 起 — SubscriptionOrder 持久化版本化结账快照、哈希、预期金额/币种/产品/模式及 review/resolution 字段；UserSubscription 固化套餐标题和额度重置策略。 model/subscription_checkout.go:389、907 起 — CreatePendingSubscriptionOrder 在远端请求前冻结套餐和支付契约；CompleteSubscriptionOrder(VerifiedSubscriptionPaymentFact) 精确校验 provider、交易/结账标识、金额、实付、币种来源、产品、方式、模式、快照与 payload hash，并只按快照授予权益。 model/subscription_checkout.go — SubscriptionPaymentReceipt 形成 provider+transaction 唯一幂等边界；SubscriptionPaymentEvidence 逐次保存冲突回调的有界 canonical fact，不落原始 PII payload。 model/subscription_reconciliation.go:26、127 起 — 管理员可分页查看待核账订单，并以 grant/close/externally_refunded 追加式决策幂等处置；跨订单交易冲突禁止补发。 model/subscription_migration.go、model/main.go — 增加回执/证据/决策迁移，回填旧回执、核账元数据和权益策略；缺失套餐安全降级为不重置。 Stripe、Creem、Epay、Waffo Pancake 均传递签名覆盖的产品/快照/金额事实；本地订单先于远端会话创建，回调可用性不再依赖“允许新订单”的商品目录配置。
Why it matters：原行为会破坏支付与权益之间的可追溯一致性，使价格或套餐变更影响已经进入结账的客户，并让跨网关重复付款或交易号冲突缺少统一处置边界。
Realistic failure scenario：用户下单后、回调前管理员修改套餐有效期、额度或升级组；合法回调曾可能按新套餐创建订阅。另一现实场景是同一 provider transaction 被用于另一本地订单，若没有唯一回执会重复授予权益。
Outcome：套餐在下单后的修改或删除不再改变已付款权益；事实不一致、第二笔付款、交易号跨订单复用和历史无快照订单会进入可追踪人工核账并由 webhook ACK，但不会自动获得订阅。
Minimal fix · Implemented
订单、权益、支付预期、provider 已验签事实、唯一回执、逐事件证据和人工决策形成版本化不可变边界；余额购买也使用同一金额/回执语义。
Better long-term fix
在隔离环境补做四 provider sandbox 与真实 MySQL/PostgreSQL migration 演练，并为待核账队列增加告警/仪表盘和 provider 原生退款自动化。
Regression test suggestion：持续保留不可变快照、套餐修改/删除、金额/实付/币种/来源/产品/方式/模式/hash/checkout ID 不一致、超长金额/支付方式、重放、第二笔付款、跨订单交易复用、legacy pending、余额购买、reset 策略、迁移、四 provider 事实、核账 ACK/DB 重试与管理员幂等处置用例；最终 backend preflight 已通过。
Estimated effort：代码整改已完成；生产 provider sandbox 与 MySQL/PostgreSQL 演练预计另需 1–2 天和隔离环境/凭据。

R02. 仓库默认恢复链路仍是同机恢复点，且本轮没有真实灾备演练

High Confidence: High
📁 Category: Recovery / Release 📌 Status: Confirmed in repository · External production state unknown 📍 Affected area: deploy/ops/lib.sh；deploy/ops/backup.sh；deploy/ops/README.md；deploy/ops/go-live.md
Problem：代码层已能生成一致的 MySQL/Redis/配置恢复集，但默认保存在同一主机；整机、磁盘、账号或勒索事件可能同时摧毁生产与备份。本轮遵守用户要求，没有启动 Docker、没有改服务器，因此也没有证明真实 RTO/RPO。
Evidence： deploy/ops/lib.sh:49-52 — BACKUP_DIR 默认 /root/backups，KEEP 默认 7。 deploy/ops/README.md:82 — runbook 明确把这些产物定义为同机恢复点而非完整灾备。 deploy/ops/go-live.md:134-142 — 默认 cron 是每日全量，异地/对象存储外迁仍是人工建议。 deploy/ops/backup.sh:141-166 — 配对 manifest、SHA-256、权限与一致性校验完整，但没有自动远端复制、不可变保留或 PITR 链路。
Why it matters：备份脚本正确不等于灾备可用。没有异地、不可变副本和定期真实恢复演练，最严重故障下仍可能无法恢复或恢复时间不可预测。
Realistic failure scenario：宿主磁盘损坏或 root 账号被攻破，同机 /root/backups 与运行数据一起丢失；团队直到事故时才发现对象存储复制、密钥或恢复步骤不可用。
Minimal fix
把每个已校验 manifest 恢复集自动加密复制到独立账号/区域的对象存储，启用不可变保留与生命周期告警；在一次性隔离主机执行完整 restore + 应用验收并记录 RTO/RPO。
Better long-term fix
为 MySQL 建立 binlog/PITR，Redis/配置保留配对版本；将恢复演练做成周期性、可审计的灾备作业，并验证密钥轮换、跨账号访问与删除保护。
Regression test suggestion：每月至少一次从远端对象恢复到空环境，核验 manifest/hash、数据计数、关键财务不变量、应用 readiness 与回滚；演练失败必须告警。
Estimated effort：1–2 天建立远端复制与首次演练；PITR 另计

R03. 生产 Compose 使用应用 DB root、无认证 Redis，并依赖可变基础镜像 tag

Medium Confidence: High
📁 Category: Configuration / Least Privilege / Supply Chain 📌 Status: Confirmed 📍 Affected area: deploy/docker-compose.test.yml
Problem：一旦应用容器被利用，攻击者直接获得数据库最高权限；同网络内任意受控容器可访问 Redis。基础镜像 tag 也可能在重建时指向不同制品。
Evidence： deploy/docker-compose.test.yml:23-24 — 应用 SQL_DSN 使用 MySQL root，Redis URI 没有认证信息。 deploy/docker-compose.test.yml:74-86 — MySQL 镜像为 mysql:8.2，root 密码被强制注入，但应用权限仍是 root。 deploy/docker-compose.test.yml:93-105 — Redis 为 redis:7.4.9-alpine、无 ACL/口令；MySQL 与 Redis 都未用 digest 锁定。 缓解因素：两项数据服务没有发布宿主端口，位于 Compose 内网。
Why it matters：这扩大单点入侵的影响面，也让灾难恢复和发布复现依赖远端 tag 当前状态。MySQL 版本迁移涉及认证与持久化参数，不能未经演练直接替换。
Realistic failure scenario：上游解析器或管理端点被利用后，攻击者从 app 容器以 root 删除/改写全库，并篡改 Redis 风控键；之后用同一 tag 重建得到不同镜像，增加取证与恢复不确定性。
Minimal fix
创建专用应用 DB 用户并仅授予所需 schema 权限；为 Redis 配 ACL/口令并轮换；在隔离环境演练 MySQL 8.4 LTS 后固定补丁版本和镜像 digest。
Better long-term fix

R04. 批量配置只在数据库内原子，运行时仍逐字段发布裸全局

Regression test suggestion：并发更新与高频读取测试在 -race 下运行，断言读者只能看到旧版本或新版本，永远看不到混合字段；覆盖失败发布与重启重载。

R05. 认证缓存失效在 DB 提交后失败时，仍存在短暂旧授权窗口

Medium Confidence: High
📁 Category: Authentication / Distributed Cache 📌 Status: Confirmed bounded failure window 📍 Affected area: model/auth_cache_generation.go；model/user.go；model/user_cache.go；model/token.go；middleware/auth.go
Problem：短暂 Redis 故障如果发生在 DB 已禁用/删除用户或令牌之后，其他实例可能继续命中旧 hash，直到 TTL 到期；持续 Redis 故障会回源 DB，因此风险是短暂失效失败后恢复的有界窗口。
Evidence： model/user.go:529-549 — 用户 DB 更新先完成，随后失效 Redis；失效失败返回错误，但没有持久重试/outbox。 model/user_cache.go:84-100 — 认证读取优先返回 Redis 命中，Redis miss/error 才回源 DB。 model/auth_cache_generation.go:39-104 — generation + Lua CAS 已阻止健康 Redis 下的并发旧填充，但生成与 DB 提交不是分布式事务。 common/init.go:110-114 — 默认缓存 TTL 约 60 秒。 middleware/auth.go:426-437 — TokenAuth 使用缓存中的用户状态做放行决定。
Why it matters：禁用与撤销是安全控制，调用方收到错误并不能撤回已提交 DB 变更，也不能保证其他实例停止使用旧授权。
Realistic failure scenario：管理员禁用被盗令牌时 Redis 短暂超时，DB 更新成功但失效失败。Redis 随即恢复，另一实例在剩余 TTL 内继续接受旧缓存。
Minimal fix
为撤销敏感实体增加 DB auth_version/disabled_at 并在缓存值携带版本；失效失败写入持久 outbox 重试。高风险管理操作可在成功响应前验证全局失效或启用短期 DB 复核。
Better long-term fix
构建可审计的授权版本/deny epoch 协议，实例按单调版本拒绝旧缓存；将缓存失效与事件发布纳入事务 outbox。
Regression test suggestion：模拟 DB commit 成功、Redis invalidation 失败、Redis 恢复、另一个实例旧缓存命中的完整时序，断言旧版本立即被拒；覆盖用户、token、硬删除和额度更新。
Estimated effort：2–3 天
