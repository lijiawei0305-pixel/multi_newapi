📝 Executive Summary / 总体评估

📋 审计结论

项目概况：这是一个 Go 1.25+、Gin、GORM 的多供应商 AI API 网关，支持 SQLite/MySQL/PostgreSQL、Redis、多租户计费与 React 管理端，同时包含 Classic、Default、Orbit 与 Electron 多个交付面。本次更新以已发布基线 da99ecd 为起点，审查并固化了 R02–R08 整改。

结论：整体代码健康度为 8.3 / A。当前开放发现为 1 个 High、2 个 Medium、0 个 Low：R02、R03 已完成仓库侧 fail-closed 路径但现网尚未迁移，R06 经 GitHub API 证实两个 Environment 均不存在。R04、R05、R07、R08 已关闭。外部前置条件完成前，不允许部署本批改动。

本轮亮点：支付、认证/OAuth 和模型限流配置改为一次发布的不可变快照；用户/Token 撤销在 DB commit 前建立 Redis fence，commit 后由持久 outbox 幂等释放；Realtime WebSocket 默认同源并在 TokenAuth 前拒绝未知 Origin；整改拆成 4 个清晰提交，并增加干净 checkout、异地加密复制、数据服务最小权限与 GitHub Environment 只读门禁。

审计边界：没有调用 Claude、没有启动本地 Docker、没有部署或修改服务器/GitHub 设置。执行了服务器与 GitHub 的只读核验；远端基线 CI 和一次性 MySQL+Redis restore drill 均成功。没有执行生产凭据轮换、MySQL 8.4 升级、真实异地副本 restore、支付/provider 沙箱或生产压测。

R01. 已修复：原生订阅订单已固化不可变结账/权益快照，并按已验证支付事实完成

Resolved Confidence: High
📁 Category: Data Integrity / Payment 📌 Status: Remediated · Code-level verified ⚠ Historical severity: High 📍 Affected area: model/subscription*.go；controller/subscription_payment_*.go；controller/topup_*.go；router/api-router.go
Problem（历史）：下单时的套餐权益曾不是订单的不可变事实，回调完成时会读取可能已被管理员修改后的当前套餐；模型完成接口也缺少统一的网关金额、币种、产品与模式事实。
Evidence： model/subscription.go:108 起 — SubscriptionOrder 持久化版本化结账快照、哈希、预期金额/币种/产品/模式及 review/resolution 字段；UserSubscription 固化套餐标题和额度重置策略。 model/subscription_checkout.go:389、907 起 — CreatePendingSubscriptionOrder 在远端请求前冻结套餐和支付契约；CompleteSubscriptionOrder(VerifiedSubscriptionPaymentFact) 精确校验 provider、交易/结账标识、金额、实付、币种来源、产品、方式、模式、快照与 payload hash，并只按快照授予权益。 model/subscription_checkout.go — SubscriptionPaymentReceipt 形成 provider+transaction 唯一幂等边界；SubscriptionPaymentEvidence 逐次保存冲突回调的有界 canonical fact，不落原始 PII payload。 model/subscription_reconciliation.go:26、127 起 — 管理员可分页查看待核账订单，并以 grant/close/externally_refunded 追加式决策幂等处置；跨订单交易冲突禁止补发。 model/subscription_migration.go、model/main.go — 增加回执/证据/决策迁移，回填旧回执、核账元数据和权益策略；缺失套餐安全降级为不重置。 Stripe、Creem、Epay、Waffo Pancake 均传递签名覆盖的产品/快照/金额事实；本地订单先于远端会话创建，回调可用性不再依赖“允许新订单”的商品目录配置。
Why it matters：原行为会破坏支付与权益之间的可追溯一致性，使价格或套餐变更影响已经进入结账的客户，并让跨网关重复付款或交易号冲突缺少统一处置边界。
Realistic failure scenario：用户下单后、回调前管理员修改套餐有效期、额度或升级组；合法回调曾可能按新套餐创建订阅。另一现实场景是同一 provider transaction 被用于另一本地订单，若没有唯一回执会重复授予权益。
Outcome：套餐在下单后的修改或删除不再改变已付款权益；事实不一致、第二笔付款、交易号跨订单复用和历史无快照订单会进入可追踪人工核账并由 webhook ACK，但不会自动获得订阅。
Minimal fix · Implemented
订单、权益、支付预期、provider 已验签事实、唯一回执、逐事件证据和人工决策形成版本化不可变边界；余额购买也使用同一金额/回执语义。
Better long-term fix
在隔离环境补做四 provider sandbox 与真实 MySQL/PostgreSQL migration 演练，并为待核账队列增加告警/仪表盘和 provider 原生退款自动化。
Regression test suggestion：持续保留不可变快照、套餐修改/删除、金额/实付/币种/来源/产品/方式/模式/hash/checkout ID 不一致、超长金额/支付方式、重放、第二笔付款、跨订单交易复用、legacy pending、余额购买、reset 策略、迁移、四 provider 事实、核账 ACK/DB 重试与管理员幂等处置用例；最终 backend preflight 已通过。
Estimated effort：代码整改已完成；生产 provider sandbox 与 MySQL/PostgreSQL 演练预计另需 1–2 天和隔离环境/凭据。

R05. 已修复：授权撤销在 DB commit 前建立 Redis 单调 fence

Implemented & verified
用户禁用/硬删、Token 禁用/删除、提交前 Redis 失败回滚、提交后断开恢复、旧 hash 注入、乱序 fence 与正常命中均在 race 下通过。

✅ Respected Practices / 已遵守原则
✓Fail fast / fail closed — secrets、demo seed、strict JSON 与危险 restore
✓Idempotency — 支付完成、退款、分润、订单回调与缓存 generation
✓Bounded resources — response buffer、polling、stream reader、compensation timeout
✓Explicit error handling — billing/stream/cache invalidation 不再静默吞错
✓Cross-database discipline — GORM/helper + SQLite/MySQL/PostgreSQL 兼容分支
✓Immutable cache snapshots — channel/subscription/auth generation 防 stale fill
✓Immutable checkout facts — 订单、权益、支付预期、provider 事实、回执和人工决策形成版本化边界
✓Atomic runtime publication — 支付、认证/OAuth 与限流配置只发布完整快照
✓Linearizable revocation boundary — DB commit 前 fence，durable outbox 幂等重放
✓Defense in depth — WebSocket Origin 在 token 解析前验证
✓Reproducible review — 四个意图提交、git archive HEAD、fresh worktree clean-checkout
