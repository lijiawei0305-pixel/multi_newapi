📋 总体评估

复审对象： 本会话针对上一轮增量审计（High×3 + Medium×3）所做的 5 条修复 52204cb..ed09773（F1 指纹去 UA / F2 占键两级补偿 / F3 lib.sh 惰性口令校验 / F4 收窄 force / F6 补 Del 测试；21 文件、+781/−54，其中 ~460 行是测试）。方法：2 路 opus 对抗式子代理各带 9 条「证伪假设」深挖，加审计者独立复核（含对头号发现的第一手复现），全程 go test -race 实跑、工作树复核零残留。这是「修完自己审自己补丁」的复审——目标是抓修复引入的新缺陷，而非重复原发现。

一句话结论： 修复大体扎实，但我在 F1 上修过头了——它引入了一条 High 级可用性回归，且已随 ed09773 上线生产。 好消息占多数：F2 两级补偿的三条最凶假设（双重释放、漏释放、跨用户误删）全部被证伪；F3、F4、F6 经得起对抗，18 条证伪假设里 12 条是伪警报。坏消息是 1 条真回归 + 2 条残留 + 1 处测试盲区。

头号问题（R1，High，已上线）： F1 把设备指纹从 sha256(ClientIP+UA) 改成 sha256(ClientIP)，安全推理没错（UA 是客户端可自选、不该进唯一性键）——但它移除了唯一能让同 IP 真人不碰撞的分量，而设备维度的键是 TTL=0 终身、且实名维度恒空（无 KYC）导致三维去重实际退化为 user∪device。后果：同一运营商 CGNAT / 公司 / 校园出口 IP，谁先领到 Trial，其后所有共享该 IP 的真人账号就被永久拒绝——换账号、换设备都无效（指纹只认 IP），唯一解套是人工客服后台释放。我已用独立测试第一手复现（同 IP 的 1002/1003 被拒、换 IP 的 1004 放行）。中国移动网大量走 CGNAT、单出口 IP 时分复用数百至上千订阅者，而 Trial 正是引流获客的漏斗顶端——这是结构性、永久、面广的转化损失。它把一个「潜伏危险（TTL=0 + 共享粗粒度维度）」从对合法用户休眠，转成了对 CGNAT 流量 live。

其余： R3（Medium）——F2 的 Level B 补偿用了原始 ctx 而非 context.WithoutCancel（Level A 用对了），客户端在 CreatePay 失败瞬间断连时释放会随 ctx 取消而失败 → 又泄漏一把终身键，恰是 F2 本要根除的场景；这个泄漏当前测不出，因为所有测试跑在忽略 ctx 的 MemKV 上（与 C8「SQLite 绿测盖住坏生产路径」同型）。R5（Medium/测试）——Level B 的 HTTP 触发块（CreatePay 失败→释放）零测试覆盖，若有人删掉它或传错参（错 deviceID/丢 PlanCode）无测试报红。R4（Low）——CreatePay 失败会留孤儿 pending SUB 单，但 2h 对账清扫、Trial 免费，轻微。R2（Low）——F1 在 http.go:235 写的「/24 网段可降低连坐」注释方向反了（越粗→越多人共键→连坐更重），会误导未来修复者。R6/R7 为 Info（force 张力、.env sed 尾空格，均非本次引入的真缺陷）。

做对的部分（占多数，须点名）： F2 两级补偿的时序设计是对的——defer 注册在 CheckPurchaseLimit 成功之后，所以购买前失败（含同 IP 被拒的 B）不会触发误释放；配合 ReleaseTrialLimit 的 force=false 归属校验，双保险防跨用户误删。F4 的 forceReleasable 边界是 fail-safe（合法 owner 键恒受保护、脏值恒可 force），reason 校验前置于引擎断言（fail-closed），限流中间件顺序正确。F3 穷举 6 个 lib.sh sourcer 无漏网。F6 的 5 个变异逐一杀死对应测试、并发用例 200× -race 零抖动。并发维度（Concurrency 9.0/S）几乎满分——没有引入任何新竞态。

总评：7.6 / A。 作为一次修复复审，这是「合格且大部分优秀，但有一条必须尽快回滚/收口的 High 回归」。R1 已在生产 live，是本报告唯一的紧急项——它不是 F1 方向错（去 UA 是对的），而是没同时处理病根：共享粗粒度维度上的 TTL=0 终身键。正确收口=给设备维度加有界 TTL（或把占用挪到支付成功后），同时保留 user 维度的终身去重。

问题：F1 修复的方向正确——UA 是客户端可自选字段，把它放进唯一性键确实等于让被监管方自选分桶（原 F1 发现成立）。但改成纯 sha256(ClientIP) 后，三个前提叠加把「潜伏危险」变成了对真实流量的 live 回归：
① 实名维度恒空（http.go:299 RealNameID:"" 硬编码，engine.go:342 注释自陈「当前恒空」，无 KYC）→ 三维去重 user∪realname∪device 实际退化为 user∪device；
② 设备维度 = CGNAT 出口 IP（trusted_ip.go:21 TrustedPlatform=CF-Connecting-IP → ClientIP() 返回运营商 NAT 出口 IP）；
③ 该键 TTL=0 终身（port.go:77 PurchaseDedupTTL:0，值=首占者 userID，永不过期）。

合起来：同一出口 IP，谁先领到 Trial，其后所有共享该 IP 的真人账号就被 PURCHASE_LIMIT_EXCEEDED 永久拒绝——换新账号（userK 全新可过，但 devK 撞上）、换浏览器/设备（指纹只认 IP）都无效，唯一解套是带鉴权的后台 ReleaseTrialLimit（人工客服）。与 F1 之前（IP+UA）相比是严格变坏：改前同 IP 不同 UA 得不同键、真人不碰撞；改后必碰撞。F1 关掉了「换 UA 绕过」，却移除了唯一缓解连坐的分量，而没碰真正的病根（共享粗粒度维度上的终身键）。

现实失败场景：中国移动/联通/电信移动网大量走 CGNAT（100.64/10），单出口 IP 时分复用数百至上千订阅者。某写字楼/学校/小区宽带亦共享少量公网出口。只要该 IP 下有任意一个用户曾成功领过 Trial，之后该 IP 下的所有新用户在购买 Trial 时都被永久拒绝。Trial 是引流获客的漏斗顶端（risk/port.go:41「引流体验款：需最强限购」），这直接砍掉这部分新用户的转化，且不可自愈、面广、永久。
安全侧的不对称：这道锁拦不住熟练攻击者——换 IP（VPN / 代理 / 移动数据重连即换 CGNAT 出口）就得到全新指纹、照刷不误。即反滥用收益只是「减速带」，而合法用户的连坐代价是「永久且广谱」。收益与代价严重不对称。
用户可见影响：大量真实新用户点「领取 Trial」得到「已超过限购次数」，而他们从未领过；客服工单激增；获客漏斗顶端静默流失。

把设备维度的「占用」从下单前挪到**支付/激活成功之后**——只让真正拿到 Trial 的人 消耗一个 IP 名额,而不是「点了下单没付款也占住整个 IP」。这与原 F2 的「消耗移到支付 成功后」根治方向一致,能同时消灭 R1(连坐)与占键泄漏整类。KYC 落地后再补「authenticated 真实身份」维度替代 IP,彻底摆脱 IP 粒度的先天不可信。
