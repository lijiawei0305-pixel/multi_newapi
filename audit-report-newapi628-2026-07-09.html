📝 总体评估

📋 总体评估

项目概况： newapi628 是基于 New API（One API 衍生）二次开发的多租户 API 代理分销平台——单套后端 + 多租户隔离 + 统一网关，支持普通/OEM/API 三类代理的分销、品牌定制、套餐与开放 API。栈为 Go 1.25（后端）+ React/TypeScript（前端 web/default）+ MySQL 8 + Redis + Nginx，Docker Compose 部署。自研层集中在 internal/（22 个领域子包，约 4.8 万行 Go）与 internal/mtwire/ 集成缝合层，配 113 个 Go 测试文件；前端自研约 50 个 feature 模块。本次审计**重点在自研多租户层**，New API 上游基线仅作边界标注（见覆盖矩阵）。

核心结论——这不是"屎山"。 我们独立核实了全部四条资金关键路径，均健全：额度扣减用原子 SQL（quota = quota - ?）、支付入账是先验签后取信 + CAS 幂等状态机 + 反篡改（金额一律以库内订单为准）、代理分润是带负值守卫的纯函数 + 唯一约束幂等台账、提现是托管两阶段状态机（冻结→审核→打款，原子 CAS）。跨租户隔离经逐端点核查无 IDOR（tenant_id 一律服务端派生、仓储层强制 WHERE tenant_id=?），管理端跨租户视图叠加 AdminAuth 把关。代码内可见历次审计编号（C1、M1–M5、L3）与端口/适配器式设计（internal/risk 堪称范例），工程纪律真实存在。全程无 Critical、仅 2 个 High。

主要风险： 集中在**异步/报表层与运维侧**，而非核心记账。① 后台定时任务首次 panic 即永久静默停摆——支付卡单对账、额度快照、套餐到期三个 loop 把 for range ticker.C 整体放进单个 gopool 任务，单轮 panic 会终结整个任务且无人重启、无健康告警，最坏情形是"已付未回调"的用户永不被补入账。② 刚上线的额度沉淀监控读取一列生产从不更新的 used_usd（tokenplan 计费桶未装配、生产走原生订阅桶、二者无同步），导致该功能恒显 0 消耗、100% 沉淀、买家用量恒 0%、满额告警永不触发。③ **性能成体系**：每请求同步 fsync 写库（BATCH_UPDATE 默认关闭）叠加自研 hook 的额外同步写，实测吞吐封顶 ~95rps 而 CPU 仅 75% 空闲；多处列表/明细查询无 LIMIT、全量物化到内存。④ **CI 不跑任何测试**——113 个后端测试与前端测试均无自动化门禁，质量完全依赖开发者本地跑 deploy.sh。

亮点： 资金路径的事务/幂等/CAS 纪律；internal/risk 的端口-适配器-fakes 分层；后端测试的真实性（真库 + httptest + 领域不变量断言，非桩测）；deploy.sh 的预检门（build/vet/go test -race/前端 build）+ 部署前备份 + 健康轮询 + 失败自动回滚；密钥卫生（无密钥入库、内网端点恒定时间比较 + deny-by-default）；上传双重把关（扩展名白名单 + 内容嗅探，拒 SVG/HTML）；供应链锁定（go.sum + web/bun.lock + 正规支付 SDK）。

优先修复： （1）给三个后台 loop 加逐轮 recover + 心跳/告警（半天内，最高杠杆）；（2）修 used_usd 数据源，让沉淀监控读真实用量（1–2 天）；（3）加一条跑 go test -race + 前端 build 的 CI（1–2 小时，复用 preflight.sh）；（4）开 BATCH_UPDATE 并压测校验，随后异步化自研计费写、给无界列表加分页。

总评： B（6.4）——对一个从 3 天 MVP 起步的 fork 而言，工程质量明显高于预期：核心资金与隔离逻辑扎实、后端测试可信、部署脚本成熟。扣分来自成体系的性能债、异步/报表层两个真实 High，以及"有测试却无 CI 强制、有硬约束表却全为 TODO"的护栏缺位。**核心是稳的，短板是明确且可修的**，不需要重写，属"值得在下一个发布前定向投入"的量级。

1. 后台定时任务首次 panic 即永久静默停摆（含支付对账）

High Confirmed · 已复核
📁 稳定性 / 可观测 📍 internal/mtwire/reconcile_loop.go:39-46 🎯 StartReconcileLoop / runReconcileOnce 🔎 置信度 High
问题：三个后台 loop（支付卡单对账 reconcile_loop.go、额度快照 breakage_snapshot_loop.go、套餐到期 agent_plan_expiry.go）都把整个 for range ticker.C { a.runXxxOnce() } 放进单个 gopool.Go 任务，而 runXxxOnce 内部无 recover（仅 atomic 防重入）。gopool 的 recover 在任务边界，整个循环是一个任务——循环体任一次 panic 会展开到任务闭包、被 worker 记一行 GOPOOL: panic 后任务结束，defer ticker.Stop() 触发，无人重新提交。周期任务从此永久死亡（进程不崩，作业死掉），且除翻日志外无任何存活告警。
- 文件: internal/mtwire/reconcile_loop.go:39-46 - 结构: gopool.Go(func(){ ticker:=NewTicker(); defer ticker.Stop(); runReconcileOnce(); for range ticker.C { runReconcileOnce() } }) - runReconcileOnce (:53-62): 仅 reconcileRunning.CompareAndSwap + defer Store(false)，无 recover → panic 直接上穿循环 - 同构: breakage_snapshot_loop.go:67-75 / agent_plan_expiry.go:29-38（runOnce 均无内层 recover） - 复核: gopool@v0.1.3 recover 在 worker 任务边界，for-range 全体属一个任务
最小修复（半天内 · 最高杠杆）
// 每轮调用包一层 recover，隔离单轮 panic、令循环存活 for range ticker.C { func() { defer func() { if r := recover(); r != nil { common.SysError(fmt.Sprintf("reconcile loop iteration panic: %v", r)) } }() a.runReconcileOnce() }() }
⏱ 工作量： 30 分钟（recover）+ 2-4 小时（每轮 last_success_at 心跳 + 超 N 周期无成功经 AlertSink 告警） ·  回归测试： 注入会 panic 的 runOnce 桩，断言 ticker 下一轮仍被调用（循环存活）+ 心跳时间戳前移
