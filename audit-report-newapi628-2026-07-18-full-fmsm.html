📋 总体评估

项目概况：这是一个 Go 1.22+ / Gin / GORM 的多供应商 AI API 网关，配套 React 19 Default、React 18 Classic、Electron 与 Orbit 子项目，覆盖认证、计费、支付、代理分润、多租户、风控和发布运维。审计从最新拉取点 52204cb 扩展到当前 HEAD 9315555 的完整工作树；扫描 3,708 个文件，并排除生成物、node_modules、既有审计报告和参考素材作为主结论来源。

主要风险：最大风险不是代码风格，而是资金与权益状态机：并发额度可透支、退款和批量扣费可永久丢失、支付/过期竞态可能成功 ACK 却不入账。发布侧的在线整库恢复同时遗漏 Redis 权威 Trial 键，构成 Critical 级一致性风险。

亮点：全仓 Go 测试通过，重点 internal race 通过；风险引擎最新限购键补偿和设备 TTL 有明确回归测试；主 Dockerfile pin digest，并为稳定镜像生成 SBOM/provenance/cosign；生产测试栈的敏感配置多数采用 fail-closed，Redis 也启用了 AOF 与持久卷。

优先修复：先冻结会改变资金/恢复状态的发布，修复 F01–F07 的原子性与持久化，再封堵会话/SSRF 和备份/回滚链，最后补齐真实 CI 门禁、前端体积/i18n/复杂度治理。

总评：4.1 / 10（C）。代码并非不可救，但当前存在多条可造成真实资金、权益、会话或恢复事故的路径；在关键不变量完成回归验证前，不建议把“测试通过”视为可安全发布的充分条件。

F01. 生产恢复在线覆盖 MySQL，且遗漏 Redis 权威状态

CriticalConfirmed
置信度：High类别：Data Integrity / Release / Stability影响：支付、额度、Trial 限购、恢复点一致性
问题：恢复脚本在应用仍可写入时把含 DROP/CREATE/INSERT 的 dump 导入当前生产库，完成后只“建议”重启；同时宣称 Redis 是可重建缓存而不恢复，但 Redis 实际保存没有 DB 后备的永久 Trial 去重键。
为什么重要：恢复期间的支付/扣费写可能被后续导入覆盖；DB 与 Redis 来自不同时间线会让限购历史丢失或与订单脱节。
可复现场景：导入时支付回调写入一笔订单；dump 随后覆盖该表。新机仅恢复 DB 后，历史 Trial 用户的永久 Redis 键不存在，可再次领取。
deploy/ops/restore.sh:17,45-53 — 在线导入，只建议重启，不恢复 Redis deploy/ops/backup.sh:45-54 — 已生成 redis-<ts>.rdb deploy/docker-compose.test.yml:95-105 — 注释明确 Trial 键无 DB 后备 internal/risk/port.go:71-92 — 用户/实名维度 PurchaseDedupTTL=0（永久）
最小修复
进入维护模式并停流 → 停止 app/worker → 校验无写者 → 恢复同一 manifest 的 MySQL + Redis → 启动 → DB/Redis/readiness/reconcile 全通过 → 开流。任一步失败不得报告完成。
长期修复
备份增加 manifest、成对快照 ID、checksum；优先在隔离栈恢复并验证后切换。
回归测试：Compose 演练加入 DB marker、Redis 永久键和并发 writer；恢复期间 writer 必须不可达，恢复后两类 marker 必须属于同一恢复点。 工作量：1–2 天。

F02. 钱包及 Token 额度“先查后无条件扣减”，并发可透支

HighConfirmed

问题：预扣前先读余额，随后执行不带 quota ≥ amount 条件的减法更新。
为什么重要：读取与扣减不原子，多请求可同时通过检查并调用付费上游。

使用 WHERE quota >= ? 的原子条件 UPDATE，并要求 RowsAffected == 1；Redis 模式用 Lua 原子检查扣减。
长期修复
以 request_id 建立可审计的 reserve/commit/refund 资金状态机，统一 DB 与 Redis 不变量。
回归测试：SQLite/MySQL/PostgreSQL 上以屏障并发两次超半额扣减，必须恰一笔成功且余额不为负。 工作量：2–4 天。

F03. 钱包退款/回滚是非持久、非幂等的 best-effort

HighConfirmed
置信度：High类别：Billing / Fallback影响：错误扣费、退款可靠性
问题：内存标志在异步退款真正成功前就置为 refunded，DB 失败只记日志；钱包 refund 本身是 quota += N，无法安全重试。
为什么重要：进程退出或瞬时 DB 故障会把用户预扣永久留在系统中，却没有持久重驱动依据。
场景：上游失败后安排退款，进程在 goroutine 落库前退出；重启后既无 pending 台账，也不能安全重复退款。
service/billing_session.go:81-122、152-170、256-267 service/funding_source.go:57-64 — 钱包退款非幂等，无法安全重试
最小修复
事务写入 request_id 唯一的 refund_pending；可重试 worker 以 CAS 推进至 refunded，首次失败不得丢弃。
长期修复
把预扣、结算、退款统一为持久双录账本并定期对账。
回归测试：首次退款写故障、第二次成功；重启后补偿且最终只退款一次。 工作量：2–4 天。

显式状态迁移表 + event inbox/outbox，支付事实优先且可重放。

F06. AGT 激活先做副作用、后做且不检查 CAS，与过期任务竞态

长期修复
采用事务 outbox/saga，使外部副作用可幂等补偿，所有状态迁移有唯一所有者。
回归测试：固定回调/过期竞态，结果只能是 activated+完整交付或 expired+无副作用。 工作量：2–4 天。
