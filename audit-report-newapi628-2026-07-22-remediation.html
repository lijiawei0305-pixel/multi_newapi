📝 Executive Summary / 总体评估

📋 审计结论

项目概况：newapi628 是以 Go、Gin、GORM 为核心的多供应商 AI API 网关，覆盖 SQLite、MySQL、PostgreSQL、Redis、认证、计费、多租户、Default/Classic/Orbit Web 与 Electron。本轮从原始 8 个发现出发，由 3 个子 Agent 分域修复，再按 Fuck My Shit Mountain full 模式复审 25 个维度。

结论：整体提升为 8.9 / A。原 F02、F05、F06、F07、F08 已确认修复；F04 的生产最小权限部分已由只读证据确认，仓库侧 MySQL 8.4.10 恢复矩阵也已补齐。当前没有已知的仓库内可执行 bug，剩余 3 个外部项：1 High、2 Medium，不能通过继续改本地源码诚实地关闭。

主要成果：Web/Electron/Orbit 依赖审计归零；Go reachable vulnerability 归零；SA* 静态分析归零；全部生产源码低于 1500 行且零白名单；Node/Actions、镜像、Gitee 同步、Electron 签名和恢复矩阵均变为可回归、fail-closed 的门禁。

边界：本轮修改仅存在于本地工作树，未 commit、未 push、未部署、未变更 GitHub Environment。未运行生产破坏性恢复、生产 MySQL 迁移、真实签名发版、人工无障碍旅程或生产负载测试。

🔍 Detailed Findings / 详细发现

F01. 远端不可变副本尚无端到端恢复证明

Severity: HighConfidence: Medium
📁 Category: Stability / Data Integrity / Release📌 Status: Suspected / external📍 Affected area: production offsite backup and disaster recovery
Evidence： deploy/ops/README.md:86-88,106 — 明确说明对象锁/跨账号保留和真实远端恢复属于外部证明。 deploy/ops/offsite-copy.sh:2-12,101-120 — 支持 fail-closed 异地复制、manifest 与 SHA 回执。 生产只读证据 — BACKUP_OFFSITE_REQUIRED=1，age/rclone 已配置，存在 5 份 mode 600 的完整下载 SHA 回执；但未提供 Object Lock/跨账号策略，也没有由远端 version 执行 decrypt → restore → readiness → reconcile 的归档证据。
Problem：远端完整下载和哈希已证明“对象可取回”，尚未证明“密文、密钥、格式、数据库版本与恢复流程在灾难边界外可以共同恢复业务”。
Why it matters：同账号删除、密钥丢失、对象覆写或恢复格式漂移仍可能让看似健康的远端备份不可用。
Realistic failure scenario：生产主机与本地备份同时丢失，团队下载到远端对象后才发现 age identity 不可用、对象未被锁定，或备份无法通过 readiness/reconcile。
Minimal fix
归档对象存储 Object Lock/跨账号保留策略；在隔离环境从指定远端 version 下载、验 SHA、解密并完成 MySQL/Redis restore、readiness 与 reconcile。
Better long-term fix
按月自动进行跨账号远端恢复演练，记录对象 version、签名 manifest、RPO/RTO、密钥托管与不可删除期限。
Regression test suggestion：独立 runner 只允许以远端 version 为输入，新建空栈后校验 marker、schema、Redis 与账务 reconcile；结果与对象保留策略作为 release readiness 证据。
Estimated effort：0.5–1 天 + 存储/凭据协调。
Principle violated：Recoverability must be proven across the actual disaster boundary.

Why it matters：凭据泄漏或单一管理员误操作时，代码中的 tag/ref 检查不能替代独立的人为授权边界。

Regression test suggestion：定时和 release 前运行严格 Environment 审计，任何 reviewer、自审、admin bypass 或 ref policy 漂移都阻断发布。
Estimated effort：1–4 小时 + 方案/所有者迁移。
Principle violated：External release authority requires independent approval.

F03. 生产 MySQL 8.4 迁移与回滚尚无运行证据

Severity: MediumConfidence: Medium
📁 Category: Stability / Data Integrity / Operations📌 Status: Suspected / external📍 Affected area: production MySQL lifecycle
Evidence： .github/workflows/restore-drill.yml:17-36 — 本地已新增当前生产 MySQL 8.2 与候选 8.4.10 LTS 的精确 digest 矩阵。 deploy/ops/data-services-hardening.md:101-133 — 已定义候选验证、备份、维护窗口、readiness/reconcile 与回滚标准。 生产只读证据 — 应用 MySQL 账号为非 root 且仅有 schema 权限；Redis anonymous 和应用用户危险命令被拒绝；运行镜像为精确 digest。生产仍运行 MySQL 8.2。 本地 Docker daemon 不可用且变更未 push，因此尚无 8.4.10 矩阵的绿色远端 run 或生产迁移/回滚观测。
Problem：仓库准备已完成，但候选版本的真实备份兼容、升级、应用 readiness、账务 reconcile 和回滚尚未执行。
Why it matters：数据库大版本/维护版本迁移的风险来自真实数据、插件、字符集、SQL mode 与回滚边界，不能只由 YAML 静态配置证明。
Realistic failure scenario：维护窗口内升级后发现生产查询或迁移不兼容，却没有经过验证的回滚快照和明确 stop condition，导致延长停机或数据分叉。
Minimal fix
先 push 并跑通 8.2/8.4.10 restore matrix，再在生产快照克隆上执行升级、readiness、关键写入、账务 reconcile 和回滚演练，归档时间与结果。
Better long-term fix
把候选 LTS 版本、digest、恢复矩阵、生产 clone 演练和回滚 SLO 纳入周期性数据库生命周期策略。
Regression test suggestion：每次 MySQL digest 更新必须通过双版本 restore matrix 和生产数据脱敏 clone smoke；失败禁止修改生产 digest。
Estimated effort：0.5–1 天 + 维护窗口。
Principle violated：Production upgrades and rollback paths must be observed, not inferred.
