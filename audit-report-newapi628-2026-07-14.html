📝 总体评估

📋 总体评估

项目概况： newapi628 是基于 New API（QuantumNous/new-api，Go + React）二次开发的多租户代理分销平台，已上线运营，有真实付费用户（微信/支付宝充值、tokenplan 套餐订阅、/v1 API 转发按量计费、代理商分润与提现）。线上为单台 4 vCPU / 7.8 GB 服务器上的 Docker 三容器栈 newapi_test（app 监听 127.0.0.1:3100 + MySQL 8.2 + Redis），宝塔面板 + nginx 反代三域名，前置 Cloudflare。自研多租户层 internal/ 约 5 万行 Go，前端约 40 页增量。本次为“线上要害专项”，覆盖安全、稳定、性能、配置、可观测五个审计面（映射到上方 Security / Stability / Performance / Release 四个评分维度），并逐条复核了上次 2026-07-09 审计的 33 条发现；结论以源码 + 服务器只读实地取证双重印证。

主要风险： 集中在配置与运维发布层，而非业务代码。头号问题是会话/加密签名密钥是一段提交进 git 的内联默认值、且生产正在使用它（已用 sha256 比对坐实：容器运行值 == 仓库里 docker-compose.test.yml 的值）——任何能读仓库或镜像的人可伪造管理员会话、无凭据接管全平台。其次：新上线的“代理自配页脚”把未净化的 HTML 直接 dangerouslySetInnerHTML（存储型 XSS）；付费开通代理的订单在 slug 冲突时会“钱收了、代理没开、无对账、无告警”地永久孤儿；整套应用内告警在生产被禁用（支付卡单的 Critical 告警对象被静默丢弃），且对账循环每 5 分钟有 3 笔订阅失败、无人被通知；生产安全护栏 guard_not_prod 保护的是一个已删除的旧栈，导致“测试”脚本实际在对生产库执行破坏性操作。

亮点（经独立验证，非泛泛而谈）： 钱路径核心工程质量是 A 级——充值/兑换/提现/套餐激活均幂等 + CAS 状态机 + 条件式不透支更新 + 同事务资金移动；支付回调用官方 SDK 验签、金额以数据库为准（前端无法篡改价）；多租户隔离纪律良好（自研 handler 一律用中间件校验过的 tenant_id、不信客户端传入）；无 SQL 注入、无 os/exec、无硬编码业务密钥、上传有双重类型校验；外部调用普遍有超时 + 有界退避重试。上次两条 High 均已确认修复（对账循环逐轮 recover、额度沉淀监控改读真实用量列），且一次合并语义互撞被单测当天拦下——CI 门确实生效。计费写放大（上次 Medium）也已修复并部署生效。

优先修复： ①（当天）轮换并从 compose 移除 git 里的 SESSION_SECRET/CRYPTO_SECRET，改 ${VAR:?} 强制注入；②（当天）后台开启 breakage_alert_enabled + 收件人，让支付告警真能发出；③（本周）修 guard_not_prod 指向真实生产栈、给破坏性脚本加确认门；④（本周）页脚渲染接入已打包的 DOMPurify；⑤（本周）AGT 订单购买时校验 slug + 补对账兜底/告警；⑥（本周）删 healthcheck.sh 里退役 auth-service 检查并接告警 webhook、修复 nginx 死后端。

总评：5.0 / B（Fair，需要投入）。 需要说明方向：上次全维度审计 6.4，本次五维专项 5.0，并非项目质量退步——上次的 2 条 High 全部修好了，业务核心比上次更稳。分数下降是因为本次聚焦深挖了配置与可观测两个上次未深挖的面、并首次上服务器实地取证，挖出了一批只有在线上才看得见的要害（git 提交的密钥、生产禁用的告警、健康检查“狼来了”、nginx 死后端、订单孤儿）。这些绝大多数是部署配置层问题、多为小时级修复，不涉及代码架构重写。把这几处运维发布短板补齐，整体可迅速回到 A 区间。

1. 会话/加密签名密钥是 git 提交的内联默认值，生产正在使用 → 管理员会话伪造

Critical Confirmed
📁 安全 / 发布（配置） 📍 deploy/docker-compose.test.yml:17 · common/init.go:49-63 · main.go:191 🎯 会话签名 + 加密 HMAC 密钥
问题： 会话签名密钥 SESSION_SECRET（以及派生的加密 HMAC 密钥 CRYPTO_SECRET）在生产环境使用的值，是一段写死在 docker-compose.test.yml 里、随仓库提交进 git 的 48 字符十六进制默认值。服务器 .env 没有设置该键，于是 compose 的内联默认 ${SESSION_SECRET:-4329…} 生效。common/init.go:49-63 仅在密钥等于上游占位符 "random_string" 时才 fatal，这段提交的 hex 直接通过、无任何警告。CRYPTO_SECRET 未设 → fallback 为同一值，所以会话签名与 GenerateHMAC（token 缓存、文件服务）共用这把公开的钥匙。
主审计员线上验证（脱敏，仅比对不读值）： • 容器 newapi_test-app-1 printenv SESSION_SECRET → 长度 48 • sha256(容器运行值) == sha256(compose 内联默认值) ***MATCH*** • 服务器 .env 键清单：AUTH_SIGN_SECRET / MT_INTERNAL_SECRET / MT_SITE_IP / UPSTREAM_* —— 无 SESSION_SECRET、无 CRYPTO_SECRET • /api/status 进程自报正常，未触发 init.go 的 random_string fatal 证据链：main.go:191 cookie.NewStore([]byte(SessionSecret)) → controller/user.go:138-141 签名 cookie 携带 id/username/role/status
攻击路径： 攻击者读取仓库中的 docker-compose.test.yml（或从镜像中提取），用已知密钥离线构造一个 role=100（root）、id 任意的合法签名会话 cookie，直接以站点管理员身份通过真实域名登录——无需凭据、无需任何 CVE。全租户/用户/计费接管；同一把已知密钥还可伪造任意 GenerateHMAC 输出。攻击前提：能读到仓库或容器镜像（协作者、CI、镜像分发、任何一次源码泄漏）。
最小修复（当天 · 需轮换）
1) compose 改为强制注入：SESSION_SECRET: "${SESSION_SECRET:?must be set}" 2) 生成新的强随机 SESSION_SECRET 与独立 CRYPTO_SECRET，仅写入服务器 .env（权限 600） 3) 立即轮换（当前值已烧毁）并使现有会话失效（用户需重新登录） 4) 加固 common/init.go：拒绝空值 / 含 "change-me" / 长度或熵不足的密钥，不止拦 "random_string" 5) CI 增加 grep 门：禁止任何 docker-compose*.yml 出现非 ${...} 的内联密钥字面量
⏱ 工作量： 1–2 小时（改动 + 轮换 + 重部署；唯一用户可见影响是强制重新登录）  ·  回归测试： 启动集成测试断言 SESSION_SECRET 为空时进程非零退出；CI grep 门在 compose 出现内联密钥时失败。

3. 付费开通代理订单在 slug 冲突时永久孤儿：钱收了、代理没开、无对账、无告警

High Confirmed
