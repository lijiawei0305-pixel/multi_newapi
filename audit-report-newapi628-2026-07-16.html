📝 总体评估

📋 总体评估

项目概况： newapi628 是基于 New API（github.com/QuantumNous/new-api）二次开发的多租户 AI API 代理分销平台，Go 1.25 + React/TS + MySQL 8 + Redis，单服务器 Docker 单栈（newapi_test，4vCPU/7.8G）承载三个公网域名。自研代码集中在 internal/（301 个 Go 文件 / 50,312 行 / 22 个子模块），通过仅 8 个「接缝」文件挂接上游基线，前端 web/default 1202 个 ts/tsx / 21 万行。本次为 full 模式全量审计，覆盖全部 25 个维度，采用 1 名主审员 + 15 个并行子代理，并对每条 Critical/High 做了独立复核与线上只读取证。

主要风险： 两条 Critical 同时成立且互相独立。第一条是本次新发现且此前三次审计均未察觉：distribution.go:272 的 total := perCode * int64(body.Count) 溢出发生在校验之后、amount_usd 又只有下界没有上界，溢出回绕成小正数（506）后穿过代理唯一的付费闸门——代理花 $0.001 即可铸出 37 张 × $997,121,301,281.60 的兑换码，且可无限重复。第二条是 07-14 已报至今未修：生产容器在用的 SESSION_SECRET 与 git 仓库中 docker-compose.test.yml:17 的内联默认值 sha256 逐字节相同，且 CRYPTO_SECRET 未设 → 回落为同一把 → 会话签名与 HMAC 共用一把已入库的密钥。此外，发布维度（2.5/D）整体失守：生产跑的是哪份代码答不出来。

亮点（不是客套，是本次审计的实测结论）： 这不是一座屎山。架构底子相当扎实：依赖图是干净 DAG（go build ./internal/... 通过即证无环）、六边形架构在 15 个模块一致落地、88% 导出函数有 doc comment 且 0 处违反 Go 命名惯例、1009 个函数只有 5 个超 100 行、handler 层 284 处统一 respondErr 对 5 处裸 c.JSON。工具面近乎无瑕：go vet ./internal/... 与 staticcheck 零告警、go test -race ./internal/... 33 包全过 0 DATA RACE、线上 24 小时零 panic。资金路径的原子条件 UPDATE 与幂等台账是教科书级（充值入账用「唯一约束错误」而非 RowsAffected 判幂等，并在注释里写明了为什么）。fork 接缝设计（8 个文件、每个 1–3 行、经注册式钩子）把上游 rebase 冲突面压到近乎为零，是本项目最聪明的一手。

优先修复： 按「性价比 × 真实风险」而非机械按 Severity：① 兑换码溢出（30 分钟，加两行边界检查，堵住无限印钞）；② 轮换 SESSION_SECRET/CRYPTO_SECRET 进服务器 .env + compose 改 :?required（1 小时）；③ 页脚 XSS 换成仓内现成的 HtmlContent（1 行，已挂 2 天）；④ relay-claude.go:254 加 , ok（10 分钟，唯一已实测复现的 panic）；⑤ npm overrides 从成员挪到 workspace 根（30 分钟，一次解开 11 条全部失效的安全 pin）。前五项合计约 3 小时，能消掉两条 Critical 和三条 High。

总评： 4.6 / C（上次 07-14 为 5.0 / B）。分数下降不代表代码变差了——恰恰相反，工程质量本身在提升（CI 补了 -race 真门、对账告警是真修不是纸面修、计费写放大已优化）。下降是因为本次挖到了一条比此前所有发现都严重的 Critical（无限印钞），且 07-14 那条 Critical 与 5 条 High 两天过去一条未修。这个项目的处境很具体：骨架配得上生产，几个关键螺丝没拧。危险的不是「烂」，而是它看起来足够正规，以至于两条能直接变现的漏洞藏在一堆写得很好的代码中间没人怀疑——本次三个子代理同时看兑换码那段，两个给了错误的「被 INT32 挡住」理由、一个直接否定，只有实测线上 schema + 亲自算穿利用链才定的案。
